# Anstoss end-to-end management: rethink and build plan

Date: 2026-09-14. Branch: `develop`. Scope: home, event flow, chat flow, every
tab, and the admin surface behind them. Goal as stated: the app should run a
club's week end to end, not just display it.

This is grounded in a read of the current code and API, not in preference.
Where a claim below is about what exists today, it was checked.

---

## 1. What the app is for, in one loop

A Kreisliga club runs on a weekly loop. The app should carry that loop, and
every screen should be a step in it or get out of the way.

```
PLAN            COLLECT            PREPARE           PLAY              REVIEW
create event -> availability  ->  lineup, duties -> check-in, live -> attendance,
edit / cancel   nudge, deadline    kit, carpool      score, MOTM       stats, dues
```

Today the app covers PLAN (create only), COLLECT (well), PLAY (well) and parts
of REVIEW. It does not let a coach change plans once made, and PREPARE is
scattered across seven hidden routes. That is the gap the user is feeling as
"not end to end".

---

## 2. Findings that shape the plan

Each of these was verified in code. They are ordered by how much they hurt.

**F1. A coach cannot edit or cancel an event in the app.**
`event-detail.tsx` exposes reminders, attendance and check-in to managers, and
nothing else. The API has both: `PATCH /clubs/:id/events/:eventId` (title,
type, date, location, notes) and `DELETE`, which is a soft cancel that stamps
`cancelledAt`. Training rained off? The coach has no button. Today the only
way is to message everyone in chat.

**F2. Cancelling an event notifies nobody.**
`EventsService.cancel()` writes `cancelledAt` and returns. No push, no socket
emit, no chat post. `update()` does emit `eventUpsert` on the socket but sends
no push either. Once F1 ships, this becomes the next thing a coach hits: they
cancel, and the squad still turns up.

**F3. Two surfaces for one team.**
The Squad tab shows a health summary and a player list; the hidden Roster
"workspace" (`href: null`, 1,668 lines) has four internal tabs: squad,
operations, medic, kit. Squad pushes into Roster for anything real. A coach
sees the team through two doors that look different and overlap.

**F4. Home bodies for coach, admin and parent are still card stacks.**
The player home was rebuilt around one decision. The other three roles got the
identity row and the colour and copy corrections, but their bodies are
unchanged: a "do this next" card followed by three to five equal-weight cards.

**F5. Admin is a link list, not a workspace.**
`admin-dashboard.tsx` is ten `ListRow`s in four groups (people, structure,
growth, money). It answers "where is the members screen", not "what needs me
today". Pending join requests, unpaid dues and a team with no coach are all one
tap deep with no count on the door.

**F6. Announcements live in two places.**
Coaches post announcements through `AnnounceSheet` on home; players read them
in an "Announcements" channel in chat and in the home pulse. Same object,
three surfaces, no single place where "what did the coach say" lives.

**F7. Create-event is one long form.**
Type, title, date, time, team, location, notes on one sheet. Two of those
fields (team, title) are almost always the same as last time. There is no
"same as last Tuesday", no duplicate, and no recurrence (the API has no
recurrence model either).

**F8. The Profile tab is a settings list with an admin section bolted on.**
"Profile" opens the More screen: account, club, admin, app, data. Admin tools
are a sub-section of settings. For an owner that is the wrong altitude.

## 3. Information architecture

Five tabs for every club role. Same tab bar, role-aware contents. Free agents
keep their separate bar.

| Tab | What it is | Replaces |
|---|---|---|
| **Home** | The one thing to do next, then the week. Role-aware body. | Home (all roles) |
| **Schedule** | Every event, answerable inline, with create / edit / cancel for managers. | Events |
| **Chat** | Channels and DMs. Announcements are a pinned surface inside the team channel, not a second place. | Chat |
| **Team** | One team surface: people, availability, operations (medic, kit, duties, carpool), all as sections of one screen. | Squad + hidden Roster |
| **You** | Profile, contributions, settings, legal, sign out. No admin here. | Profile / More |

Admin gets a proper front door: a **Club** entry on Home (owners and admins
only) that opens a workspace, not a link list. See §6.

Navigation grammar, per the app-design skill: tabs are peers; create / edit
are modals with their own Cancel and Save; destructive confirms are action
sheets; a completed create lands back on the schedule with the new event
visible, never on a blank state.

## 4. Slices

Each slice is independently shippable and verified on the simulator before it
is called done. Order is by user impact divided by risk.

### Slice A. Event management: edit, cancel, duplicate (F1, F2, F7)

Mobile
- `event-detail`: a manager menu (native context menu on the header action)
  with **Edit**, **Duplicate**, **Cancel event**. Cancel confirms via action
  sheet with an optional one-line reason. A cancelled event renders as a
  cancelled card everywhere it appears (schedule row, home, detail) with the
  reason and who cancelled it, rather than vanishing.
- New `edit-event` modal: the create form pre-filled, saving via PATCH.
- `create-event`: split into two steps. Step 1 is the three things that
  change every time (type, date, time) with the team and title defaulted from
  the last event of that type. Step 2 is location and notes, collapsed by
  default. A "Repeat last {type}" shortcut at the top of step 1 pre-fills
  everything.

API
- `cancel()` and `update()` must notify. Add a push to every RSVP'd member
  (YES and MAYBE at minimum) using the existing push templates module, a
  socket `eventUpsert` on cancel (update already has it), and a system message
  into the team channel ("Training on Tue 19:30 was cancelled: pitch frozen").
  The chat controller already has a system-message path (`messages/lineup`
  uses it), so this is wiring, not new infrastructure.
- Accept an optional `reason` on cancel; persist it. One column, one Zod field.

Acceptance
- Coach cancels from the detail screen; every YES/MAYBE player gets a push;
  the team channel shows the cancellation; the schedule row shows it struck
  through with the reason.
- Editing the date re-opens RSVPs (existing answers are kept but flagged
  "answered before the change") and notifies.
- Maestro: `coach-flow` extended with create, edit, cancel, and a player-side
  assertion that the cancelled card renders.

### Slice B. Team tab: one surface (F3)

- Merge the Squad tab and the Roster workspace into one **Team** screen with
  sections, not nested tabs: **People** (roster with role, availability for
  the next event, and a quick "message" action), **Health** (the existing
  squad-health summary, moved up), **Operations** (medic, kit, duties,
  carpool, trials, each as a row with a live count that opens the existing
  screen).
- The Roster route stays as the detail for operations, reachable only from
  Team. Its four internal tabs become the four Operations rows.
- Players see People and their own operations (my duties, my kit). Coaches
  and admins see all of it.

Acceptance: a coach reaches any operations screen in one tap from Team; a
player finds a teammate and messages them in two taps; the Squad tab no
longer pushes into a second "roster" surface.

### Slice C. Coach and admin home bodies (F4)

Same shape as the player home, different contents.

Coach: identity row, then **Next match readiness** as the single loud card
(the existing `EventReadinessCard` promoted to hero, with the nudge action
inline), then **This week** (the schedule list with inline availability
counts), then **Team pulse** (chat, announcements), then season stats last.
The "Do this next" card is removed; its action becomes the hero's action.

Admin: identity row, then **Needs your attention** as the hero. It is a
computed list, not a card stack: pending join requests (count), members with
overdue dues (count), teams with no head coach, incomplete club setup. Each
row opens the screen that resolves it. Then the same week list and team
pulse as coach. Club-wide stats last.

Parent: identity row (which child, which team), the next event for each child
as one card each with inline availability on the child's behalf, then chat.

Acceptance: each role's home fits without scrolling on an iPhone SE-class
height for the common case; no role sees more than one loud surface.

### Slice D. Club workspace for admins (F5, F8)

- A **Club** card on the admin home (and a header action) opens
  `admin-dashboard`, rebuilt from a link list into three sections with
  counts: **People** (members, requests *n*, staff, families), **Structure**
  (teams and coaches, stats, official team pages), **Money** (dues overview
  with paid / pending / overdue, sponsors, billing). Rows carry the number
  that matters so the screen answers "what needs me" before it is tapped.
- Remove the admin sub-section from the You tab. Owners and admins reach the
  workspace from Home. The You tab becomes purely personal.

Acceptance: an owner can see pending requests, overdue dues and coach gaps
without opening any screen; nothing that was reachable before becomes
unreachable.

### Slice E. Chat: one place for what the coach said (F6)

- Announcements become a pinned, filterable surface inside the team channel
  (the existing `PinnedBanner` pattern extended into a "Announcements" filter
  chip), and `AnnounceSheet` posts into that channel as an announcement
  message type. The separate "Announcements" channel is folded in.
- Compose actions for managers from the channel: Announcement, Poll (exists),
  Share lineup (exists), Share event (new: posts a rich event card that
  carries the RSVP control inline, so answering from chat is possible).
- Composer stays where it is; the keyboard fix from this branch holds.

Acceptance: a player finds the last announcement in one tap from Chat; a coach
can post an event into chat and see replies land as RSVPs.

### Slice F. Schedule polish (after A)

- Week grouping with a sticky month header; "Needs your reply" stays pinned.
- Manager row actions via long-press context menu: edit, duplicate, cancel.
- Past events show attendance outcome in the row (14 of 18) for managers.

### Slice G. Dark mode switch-on

Independent of the above but blocked on a per-screen pass. `app.json`
`userInterfaceStyle: "light"` is the only thing holding it off. Flip it after
Slices A to E land so the new screens are audited once, not twice.

## 5. What is deliberately not in this plan

- **Recurring events.** The API has no series model. Building one is a
  backend slice with migration, a series editor, and "edit this / edit all"
  semantics. "Repeat last training" in Slice A gets most of the daily value
  for a fraction of the cost; recurrence is a follow-up once that is in use.
- **A new chat backend.** Everything in Slice E rides the existing channels
  and message types.
- **Design system changes.** Tokens, primitives and the one-accent rule from
  this branch stand. Slices use them; none redefines them.
- **Appllama reference research.** The methodology skill is followed; the
  reference-screen library needs the Appllama MCP server, which is not
  connected in this environment. If it is connected before Slice B or C, those
  two get a reference pass first.

## 7. Order and verification

A, then B, then C, then D, then E, then F, then G. A first because it is the
gap a coach hits every week and it needs the one backend change. B before C
because C's coach home links into the Team surface.

Every slice: typecheck, lint, unit tests, the six-locale parity guard, and a
Maestro flow run by exit code on the iPhone 17 Pro simulator. Screens are
checked in light and, once G lands, dark.

Nothing is pushed to `develop` without being asked.
